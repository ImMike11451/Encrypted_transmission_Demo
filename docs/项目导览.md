# 项目导览

## 项目简介

这是一个 C++17 加密传输 Demo：两个命令行客户端先与服务端协商各自的会话密钥，发送方以 AES-GCM 加密文本，服务端验证密钥状态后解密，并使用接收方会话密钥重新加密、存储和审计。项目重点是把网络通信、密码学接口、Protobuf 协议、MySQL 持久化和可测试的查询授权放在同一条可阅读的工程链路中。

项目采用可信服务端模型，定位为本地学习和演示系统，不是生产级或端到端加密产品。

## 技术栈与工程证据

| 技术 | 代码或工程证据 | 用途 |
| --- | --- | --- |
| C++17 / CMake | `CMakeLists.txt`、客户端和服务端子目录 CMake | Linux/WSL2 构建与目标组织 |
| TCP、epoll、线程池 | `TcpSocket`、`EpollServer`、`ThreadPool` | 短连接请求处理 |
| OpenSSL | `RsaCrypto`、`AesGcmCrypto` | RSA 密钥协商相关操作与 AES-GCM 消息加密 |
| Protobuf | `MessageV2.proto`、V2 编解码器 | 统一请求/响应协议 |
| MySQL / System V 共享内存 | `mysqlOP`、`SecKeyShm` | 生命周期权威存储与本地活跃密钥缓存 |
| 分层查询与测试替身 | `MessageQueryService`、仓储/审计接口 | 查询归属校验与不连 MySQL 的测试接缝 |

## 功能说明

**为什么不是端到端加密？** 服务端需要解密发送方密文，并用接收方的会话密钥再次加密；因此服务端在处理时能访问明文。

**密钥如何过期和轮换？** 新密钥默认有效 24 小时；校验或使用密钥时才检查并推进过期状态，没有后台定时任务。同一客户端再次协商会触发旧活跃密钥轮换，不是自动周期轮换。

**查询权限如何做？** 单条查询比较声明的查询者与记录的发送方/接收方；列表仅返回该声明身份的发送记录。它是基础归属校验，而非完整身份认证，因为协议目前没有完整的身份凭据验证和会话认证。

**并发使用边界是什么？** 服务端线程池共用一个 MySQL 连接，轮换和共享内存缓存也没有整体同步，因此当前实现不保证并发轮换一致性。

**如何本地演示？** 在 Linux/WSL2 构建后执行 `bash scripts/setup-demo.sh`，再按服务端、Client B、Client A 的顺序启动。详见构建和演示文档；本页不包含真实配置或数据库凭据。
